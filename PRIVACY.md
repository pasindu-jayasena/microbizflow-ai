# Privacy notes

The booking flow needs a customer's name and contact method to process a real request. A customer record is grouped by normalized contact; the owner can search it, see appointment history, and store a private note. These records are available only through authenticated, business-scoped owner routes. The application should collect only fields needed for these purposes and avoid logging enquiry bodies or credentials. Demo mode rejects booking contacts outside the reserved `@example.invalid` domain, including phone numbers. Demo bookings store a fixed fictional name and discard visitor-supplied notes. Visitors can still type personal details into assistant messages, so the interface warns them to avoid such content. A real-data privacy review remains required before using real customer data.

The enquiry assistant runs in deterministic mode by default. If a Cloudflare Workers AI binding or compatible LLM API is configured, a visitor must explicitly opt in before their message is sent to that service. Obvious email addresses and phone numbers are redacted before the model call, but this is not a guarantee that all personal information is removed. The interface asks visitors to avoid personal details. The public demo uses fictional records and mock notifications only.

Assistant analysis records retain structured intent, processing mode, latency, review state, and an optional link to a booking. Raw enquiry text is not stored. Owner operations assistant history likewise records only intent, actor, mode, latency, and proposal decisions; it does not retain the original question. A linked booking exposes customer contact only to authenticated owners. An owner can delete a customer record once all linked bookings are terminal. This erases the contact and notes, anonymizes linked booking names, contacts, and notes, removes linked assistant analyses, and invalidates the old private booking codes. Booking status, service, time, reference, workflow and audit records remain. The owner can also run a bounded 365-day retention cleanup for fully resolved customers and unbooked assistant analyses. A smaller scheduled cleanup runs in the deployed standalone Worker; its first live outcome is not yet verified.

The fictional public demo is deployed at https://microbizflow-ai.pages.dev/. The five-workflow update is on `deploymentBranch` and is not yet deployed.

Owners can download a CSV containing names, contacts, notes, and booking history. This endpoint requires the owner session and uses `Cache-Control: no-store`; downloaded files must be handled as private data. Export is limited to 1,000 matching appointments per request.

In demo mode, the standalone scheduled Worker releases at most two pending or confirmed reservations older than 24 hours per run. It cancels and anonymizes each booking, invalidates its private code, removes linked assistant analyses, and deletes its customer record if no other booking uses that fictional contact. The status and system audit event remain. This reset has only been exercised locally and will not run from Pages Functions alone.

CRM sync records hold booking IDs, event keys, states, attempts, provider IDs, latency, and timestamps, without duplicate contact content. The public demo's mock adapter makes no external request. A HubSpot adapter is implemented but disabled in demo mode; a synthetic development test and explicit consent, provider deletion, and privacy review are needed before real customer use. After a customer is deleted, any retried CRM sync is skipped.
