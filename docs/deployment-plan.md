Recheck Wrangler `whoami`, project/database lists, GitHub owner and verified commit identity, the clean branch, current Cloudflare Free limits, and the reported billing status. Stop on any conflict or pre-existing resource name.
2. On `deploymentBranch`, run `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:deployment-config`, `python -m unittest discover -s tests`, `npm run build`, and `npm run test:e2e` against local Pages/D1. Require green GitHub CI and review the diff. Keep secrets and `.dev.vars` ignored.
3. Run `npm run owner:prepare:production` locally to generate a 256-bit random owner password and salted SHA-256 hash in ignored `.production-owner-credentials`. Save the password to the owner's password manager; never paste it into Git, logs, or a command argument. Use only its username and hash as protected Pages secrets, then delete the local credentials file after the owner has saved the password and verified sign-in. Never reuse the synthetic local owner password. This high-entropy secret avoids the roughly 47 ms local CPU cost measured for the legacy PBKDF2 path, which may exceed Workers Free's 10 ms invocation limit. Live CPU remains to be measured.

## Approved provision and release sequence used

1. Create only `microbizflow-demo` with `node scripts/wrangler.mjs d1 create microbizflow-demo`, recording the returned database UUID. Use the default Free account and no jurisdiction or paid options. Create only `microbizflow-ai` with `node scripts/wrangler.mjs pages project create microbizflow-ai --production-branch main`. If the Pages name is unavailable, stop and revise the plan before creating another project.
2. Put the verified D1 UUID and `microbizflow-demo` name in `wrangler.toml` and `wrangler.worker.production.toml`. Set both `ALLOWED_ORIGIN` values to `https://microbizflow-ai.pages.dev`; retain `DEMO_MODE="true"`, the `DB` binding, and the private Worker settings. Keep `wrangler.worker.toml` local with a placeholder D1 ID; `dev:pages` overrides its D1 ID and the API accepts its own local origin. Run `npm run check:deployment-config`, which must pass. Review and commit this public configuration on the deployment branch using the verified owner identity; push and require green CI.
3. Apply the nine migrations to that exact remote database: `node scripts/wrangler.mjs d1 migrations apply microbizflow-demo --config wrangler.worker.production.toml --remote`. Confirm the remote migration table and apply only `db/seed.sql` with `node scripts/wrangler.mjs d1 execute microbizflow-demo --config wrangler.worker.production.toml --remote --file=./db/seed.sql`. Both commands mutate the approved Free D1 database; inspect their target before execution.
4. Store only `OWNER_USERNAME` and `OWNER_PASSWORD_HASH` from the ignored credentials file with `node scripts/wrangler.mjs pages secret put KEY --project-name microbizflow-ai` using protected interactive input. Never upload or deploy the `OWNER_PASSWORD` value. Keep `WEBHOOK_SECRET` and AI bindings unset. Verify the Pages configuration contains only `DB`, demo variables, and the two owner secrets.
5. Fast-forward the reviewed deployment branch to `main` using only the verified GitHub owner identity; verify the remote SHA and author/committer metadata. Build from clean `main`. Deploy Pages with `node scripts/wrangler.mjs pages deploy dist/web --project-name microbizflow-ai --branch main --commit-hash <verified-main-SHA>`. Then deploy the private scheduler with `node scripts/wrangler.mjs deploy --config wrangler.worker.production.toml`; verify the one hourly trigger and no public Worker URL. No branch preview is planned because it would expose a second public endpoint backed by the same D1 database.
6. Verify the live HTTPS page and `/api/business`, synthetic booking, private-code cancellation, owner sign-in and authorization, owner logout, demo-only contact guard, and no outbound messages. Verify D1 migrations and seed, and inspect Worker CPU, Cron outcome, request counts, and D1 row usage. Cron reset requires observing a scheduled run or safely triggering its local equivalent; do not claim a live scheduled reset until observed. Record the actual URL, SHA, checks, usage, and rollback steps in `docs/deployment.md` and `docs/progress.md`.

## Stop conditions and recovery

Stop before any paid upgrade, R2 reactivation, AI binding, custom domain, unexpected project/database, failed config preflight, failed CI, or identity mismatch. If Free CPU or row limits prevent a working demo, report the measured issue and propose a Free-compatible code fix on a new branch. Do not upgrade. A Pages deployment can be rolled back to a previously verified deployment; database migrations are backed up by Wrangler but should be reviewed before rollback. The scheduled Worker can be disabled if its Cron path fails; verify the resulting state before claiming recovery.
